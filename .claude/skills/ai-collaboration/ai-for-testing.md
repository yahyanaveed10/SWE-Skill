# AI for Testing

How to use AI generation effectively for testing, and where it fails. Tests generated by AI require more scrutiny than application code — a wrong test is worse than no test because it gives false confidence.

---

## What AI generation is useful for in testing

**Generating test case skeletons:** Given a function signature and description, AI can generate the structure of a test file quickly. This is useful as a starting point — the structure needs to be verified and the assertions need to be checked.

**Identifying input classes:** AI can enumerate boundary conditions and input classes from a function's description: nulls, empty collections, maximum values, negative numbers, malformed input. Not all generated cases will be relevant, but the enumeration is a useful starting point for human review.

**Generating parameterised test data:** Tables of input/expected output pairs for known-correct cases. Verify the expected output values — the model generates plausible values, not necessarily correct ones.

**Translating specifications to test cases:** Given a written requirement ("the function should return X when Y"), AI can draft a test that encodes that requirement. The draft must be reviewed to confirm it actually tests the stated behaviour.

---

## The AI test coverage gap

AI-generated tests systematically undercoverage:

**Side effects:** A function that updates a database, writes a file, or sends a request — AI often tests only the return value, not whether the side effect occurred.

**Failure paths:** Error handling, exception propagation, partial failure states. These are harder to prompt for and harder to generate correctly.

**Concurrency:** Race conditions, atomicity, consistency under concurrent access. AI rarely generates tests for these without explicit prompting, and even with prompting the tests may be structurally incorrect.

**Security-relevant inputs:** Injection payloads, oversized inputs, malformed encodings. These require domain-specific knowledge that AI generation does not reliably apply.

**Cross-component interactions:** Integration behaviour, behaviour at system boundaries. AI generates unit tests easily; integration test generation is lower quality.

---

## Verifying an AI-generated test

Before accepting an AI-generated test, answer:

**Does this test actually call the function under test?** Check the call site. It is possible for a generated test to assert something without exercising the target code.

**Is the expected value derived from the function's correct behaviour, or is it derived from the function's actual (possibly wrong) behaviour?** If the expected value was generated by running the function, it captures what the function does, not what it should do.

**What would make this test fail?** If you cannot describe a concrete change to the function that would cause this test to fail, the test is not testing anything. (A test that always passes is not a test.)

**Does this test tell you something meaningful when it fails?** A test name like `test_function_works` and an assertion like `assert result is not None` passes when the function returns garbage. Name tests after what they are asserting.

**Are the mocks testing the integration or mocking the integration?** A mock that always returns success regardless of input is not testing the integration. If the integration is important, test it with a real (or realistic ephemeral) dependency.

---

## Mutation testing as a calibration tool

Mutation testing (e.g., mutmut for Python, Stryker for JS/TS) systematically modifies the source code (flips conditions, changes operators, removes lines) and checks whether the tests fail. If mutations survive (tests still pass), the tests are not exercising that path.

AI-generated test suites often have low mutation scores — they cover the happy path but let mutations in error handling and boundary conditions survive.

If you have a test suite you suspect of being superficial, run a mutation test on a critical module and check the score before trusting the coverage number.

---

## When to reject AI-generated tests

Reject and rewrite when:
- The test's expected value was generated without being independently verified
- The test only covers the happy path and the function has documented error behaviour
- The assertions are structural (type checks, not-null checks) rather than behavioural
- The mock setup takes longer to understand than the function under test
- The test duplicates what another test already covers with no new scenario

A small suite of tests that assert real behaviour is worth more than a large suite that passes regardless of what the code does.
