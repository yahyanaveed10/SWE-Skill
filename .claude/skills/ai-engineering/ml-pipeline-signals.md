# ML Pipeline Signals

Signals for identifying problems in data pipelines, feature engineering, training pipelines, and model serving. These are reasoning prompts, not a checklist.

---

## Training/serving skew

**What it is:** The features computed at training time differ from the features computed at inference time. The model learns patterns that do not exist in production.

**Signals:**
- Model performs well on validation set but poorly on live traffic
- Feature computation code is duplicated between the training notebook and the serving pipeline
- Training uses batch-processed features; serving computes features online from a different code path

**Ask:**
- Is the feature computation for training and serving from the same code?
- Are the preprocessing steps (normalisation, encoding, imputation) applied identically at both stages?
- Can you feed production data through the training pipeline and get identical predictions to the serving pipeline?

**Direction:** Feature computation should be a single, versioned, tested function used by both training and serving. Not two separate implementations.

---

## Data leakage

**What it is:** Information from the future (or from the target variable) is present in the training features, making validation metrics artificially high. The model cannot replicate this in production.

**Signals:**
- Validation accuracy is suspiciously high (too good to be true)
- Model performance degrades significantly in production vs. validation
- Features include data that would not be available at the time of prediction

**Ask:**
- For every feature: would this value be available at prediction time, or does it depend on information that comes after the prediction moment?
- Is the train/validation split temporally correct? (For time-series data, validation must be strictly after training data — random splits leak future data into training.)
- Is the target variable used to compute any of the features?

---

## Data drift

**What it is:** The statistical distribution of production inputs changes over time, diverging from the training distribution. Model accuracy degrades silently.

**Signals:**
- Model performance gradually degrades over weeks or months
- No change to the model, but downstream business metrics change
- The training data is months or years old relative to current production data

**Ask:**
- What is the age of the training data relative to current production data?
- Are there known distribution shifts in the domain (seasonality, market changes, user behaviour changes)?
- What monitoring exists to detect when input distributions shift?

**Direction:** Monitor feature distributions in production and compare to training distributions. Set alerts on distribution shift metrics (PSI, KL divergence, Wasserstein distance). Retrain on schedule or when drift exceeds a threshold.

---

## Label leakage and label quality

**What it is:** Labels used for training are noisy, inconsistent, or systematically biased. The model learns the noise, not the signal.

**Signals:**
- High variance in model performance across data subsets
- Human reviewers disagree on the correct label for borderline cases
- Labels were generated by an earlier (worse) model rather than by ground truth

**Ask:**
- How were the labels generated? Human annotation, programmatic labeling, proxy labels?
- What is the inter-annotator agreement for human-labeled data?
- Are the labels representative of the actual distribution you want the model to handle?

## Batch vs. online inference trade-offs

| Dimension | Batch | Online |
|---|---|---|
| Latency | Hours to days acceptable | Sub-second required |
| Throughput | High, scheduled | Variable, on-demand |
| Freshness | Stale by design | Near real-time |
| Complexity | Lower (no serving infrastructure) | Higher (serving stack, scaling, SLOs) |
| Cost | Predictable (scheduled compute) | Variable (scales with traffic) |

**Fits batch when:** Predictions are precomputed and served from a lookup (recommendations, risk scores, ranking), the latency of model inference is not acceptable at request time, the feature computation requires data that is only available in batch.

**Fits online when:** The prediction depends on real-time context (current user state, live prices), the set of entities to predict for is not enumerable in advance, prediction is triggered by a user action that must not wait.

---

## Feature store signals

A feature store provides a shared, versioned repository of features for both training and serving. It solves training/serving skew structurally.

**Fit signals:** Multiple models share the same features, training/serving skew is a recurring problem, feature computation is duplicated across teams.

**Cost:** A feature store is significant infrastructure. Do not build or adopt one speculatively — it is justified only when the skew and duplication problems are real and recurring.
